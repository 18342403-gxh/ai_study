# 个人知识库 v5 · 产品与技术方案

> 分支：`feat/architecture-v5`
> 状态：决策已确认，待开发
> 范围：个人知识库从「组件生成参考资料库」重做为「个人记忆系统」，组件生成模块整体移除

---

## 1. 产品定义

### 1.1 一句话

用户可以随时用对话或文档把个人信息交给系统，之后所有 AI 对话都能基于这些信息作答，并且能指出回答依据的是哪条记录。

### 1.2 目标用户

个人开发商。单机使用，不需要账号体系，不与他人共享数据。

### 1.3 要解决的问题

现有知识库服务于组件生成：上传技术文档，生成组件时检索片段注入提示词。它回答的是"参考资料从哪来"，不回答"我是谁、我要做什么"。

个人使用真正缺的是后者。以下三类信息当前无处存放：

| 信息类别     | 例子                              | 特点                     |
| ------------ | --------------------------------- | ------------------------ |
| 有时效的事件 | 下周三下午两点交方案              | 过期后应失去权重         |
| 有状态的规划 | 今年系统学完前端工程化            | 需要跟踪进行中/搁置/完成 |
| 稳定的事实   | 我习惯 TypeScript，不喜欢过度封装 | 长期有效                 |

### 1.4 与现有组件生成模块的关系

v5 **彻底移除组件生成能力**：前端入口、后端 generator / agent / codegen 服务、相关路由与状态表全部删除，仓库只保留个人知识库产品。

- 旧「文档管理」升级为个人知识库的「文档」页；
- 移除后不再存在两套检索，`rag` 子系统只服务知识库；
- 旧的组件生成资料不迁移（Q5），需要时由用户自行重新导入。

### 1.5 成功标准

可观察的五条：

1. 录入一句话后，后续提问相关内容，回答里出现该信息；
2. 回答能点开引用，看到原始记录与录入时间；
3. 没有任何相关记录时，AI 明确说"没有找到"，不编造；
4. 日程过期后不再干扰新问题的回答；
5. 文档上传后，其内容能被语义检索命中。

## 3. 产品模型

### 3.1 对象关系

```
对话 Conversation
  ├─ 消息 Message
  ├─ 抽取 → 条目 Entry（draft）
  └─ 回答 → 引用 Citation → 条目 / 文档片段

文档 Document
  └─ 片段 Chunk（参与语义检索，不直接展示给用户）

条目 Entry
  ├─ 类型：schedule / plan / fact / note
  ├─ 状态：draft / active / done / archived
  └─ 向量 EntryEmbedding（用于语义检索）
```

### 3.2 条目类型

| 类型            | 判定依据                                       | 必备字段                         | 生命周期                                       |
| --------------- | ---------------------------------------------- | -------------------------------- | ---------------------------------------------- |
| `schedule` 日程 | 包含明确时间点或时间段的事件                   | 标题、开始时间；重复事件另存规则 | 到期自动归档，退出默认检索；重复事件按窗口展开 |
| `plan` 规划     | 指向未来的目标、阶段任务，通常无精确时间       | 标题、状态                       | 用户手动切换状态                               |
| `fact` 事实     | 关于用户自身的稳定信息：偏好、背景、关系、习惯 | 标题、内容                       | 长期有效                                       |
| `note` 笔记     | 不属于以上三类                                 | 标题、内容                       | 长期有效                                       |

判定优先级：能解析出确定时间 → `schedule`；含"想/计划/准备/目标"等未来意图且无确定时间 → `plan`；含"我习惯/我喜欢/我是"等自我描述 → `fact`；其余 → `note`。

### 3.3 状态机

```
draft ──确认──▶ active ──完成──▶ done
  │               │
  └──忽略──▶ 丢弃  └──到期/手动──▶ archived
```

| 状态       | 含义               | 进入方式        | 参与默认检索     |
| ---------- | ------------------ | --------------- | ---------------- |
| `draft`    | 已抽取，待用户确认 | 对话录入后      | 否               |
| `active`   | 已确认生效         | 用户点击确认    | 是               |
| `done`     | 规划已完成         | 用户标记        | 仅明确查询时     |
| `archived` | 日程过期或主动归档 | 到期自动 / 手动 | 否，仅历史查询时 |

### 3.4 为什么录入必须确认

抽取依赖模型理解，可能把"我明天可能去开会"误判为确定日程。确认这一步把错误挡在数据之外。一旦错误记忆入库，后续所有回答都会被污染，且用户很难察觉。

## 4. AI 方案

### 4.1 链路总览

**录入链路**

```
用户输入
  → 意图判别（录入 / 问答 / 闲聊）
  → [录入] 信息抽取（JSON）
  → 时间解析（相对时间 → 绝对时间）
  → 去重与冲突检测
  → 确认卡片（draft）
  → 用户确认
  → 生成条目向量
  → 入库（active）
```

**问答链路**

```
用户提问
  → 查询理解（是否需要个人信息 / 时间窗口 / 关键词）
  → 双通道检索
       A. 时间通道：SQL 精确筛选 schedule
       B. 语义通道：向量 + BM25 → RRF 融合
  → 合并、去重、加权、截断
  → 上下文组装（带编号）
  → 生成回答（强制引用）
  → 返回回答 + 引用列表
```

两条链路的共同点：**模型只负责理解和生成，检索与过滤由确定性代码完成**。这样参数可调、结果可复现，出问题能定位是检索错还是生成错。

### 4.2 分片策略

分片只作用于文档。条目本身即最小记忆单元，不再拆分；对话录入的文本也不按长度切，整段送入抽取。

#### 4.2.1 三类输入的处理方式

| 输入         | 是否分片 | 方式                                             |
| ------------ | -------- | ------------------------------------------------ |
| 对话录入文本 | 否       | 整段交给抽取模型；超过 1500 字符时按段落分批抽取 |
| 条目         | 否       | 标题 + 内容合并为检索文本，条目本身是原子单位    |
| 文档         | 是       | 结构优先 → 段落 → 长度兜底的四级策略             |

#### 4.2.2 文档分片四级策略

**第一级：按结构切（Markdown / PDF 有标题时）**

优先按标题层级切分，每个二级或三级标题下的内容作为一个候选块。块内保留标题路径作为元数据。

```
# 项目笔记
## 前端工程化
### 构建
（内容）
### 测试
（内容）
```

切分结果：`前端工程化 > 构建`、`前端工程化 > 测试` 两个块，各自带 `headingPath`。

**第二级：超长结构块按段落切**

单个结构块超过 600 字符时，按空行分段；段落之间合并到接近 600 字符为止。

**第三级：超长段落按句子切**

单段超过 600 字符且无空行时，按中文句号、问号、叹号、分号切句，累积到 600 字符为止。

**第四级：兜底硬切**

无标点的超长文本（如粘贴的日志、代码），按 600 字符硬切，overlap 80 字符。

#### 4.2.3 参数

| 参数           | 取值     | 说明                                     |
| -------------- | -------- | ---------------------------------------- |
| 目标块大小     | 600 字符 | 中文约 450 token，兼顾语义完整与检索精度 |
| 块下限         | 80 字符  | 小于此值的块并入前一块                   |
| 重叠           | 80 字符  | 约 13%，防止句子被切断后语义丢失         |
| 单块上限       | 900 字符 | 硬切兜底值                               |
| 单文档块数上限 | 500      | 超出时提示用户文档过大，建议拆分         |

> 现有 `simpleSplit` 默认 500/50，routes 里用 800/100。v5 统一收敛为 600/80，并在 `splitterPure.ts` 增加结构化分片函数，保留 `simpleSplit` 作为兜底。

#### 4.2.4 特殊内容处理

| 内容         | 处理                                                          |
| ------------ | ------------------------------------------------------------- |
| 代码块       | 整体保留，不跨块切断；超过 900 字符时按空行切                 |
| 表格         | 整体保留；行数超过 30 行时按表头 + 每 25 行切分，每块重复表头 |
| 列表         | 连续列表整体保留，不拆成单条                                  |
| PDF 页眉页脚 | 连续 3 页重复出现的短行判定为页眉页脚，入库前剔除             |
| 图片         | 本期只保留图片占位文本 `[图片]`，不做 OCR                     |
| URL 页面     | 抓取正文后先去导航、脚本、页脚，再按结构切                    |

#### 4.2.5 块元数据

每个块保留以下字段，供引用展示与调试：

```json
{
  "docId": "uuid",
  "chunkIndex": 3,
  "headingPath": ["项目笔记", "前端工程化", "构建"],
  "charStart": 1024,
  "charEnd": 1624,
  "page": null,
  "contentType": "text | table | code"
}
```

引用面板展示 `文档名 > 标题路径`，点击定位到 `charStart`。

### 4.3 信息抽取

#### 4.3.1 意图判别

不额外调用一次模型做分类，而是把判别与抽取合并成一次调用：模型先判断，再输出结构化结果。

判别规则（写入 system prompt）：

| 输入特征                                   | 判定           |
| ------------------------------------------ | -------------- |
| 疑问句、以"吗/呢/什么/怎么/多少"结尾或开头 | 问答           |
| 含时间 + 事件（"下周三要交方案"）          | 录入           |
| 含自我描述（"我习惯/我是/我住"）           | 录入           |
| 含未来意图（"打算/计划/想"）               | 录入           |
| 纯寒暄（"你好"）                           | 闲聊           |
| 同时含提问与陈述                           | 先抽取，再回答 |

#### 4.3.2 抽取输出结构

模型必须返回 JSON，不接受自然语言：

```json
{
  "intent": "record | query | chat",
  "entries": [
    {
      "type": "schedule | plan | fact | note",
      "title": "不超过 30 字的标题",
      "content": "完整描述，保留原始细节",
      "time": {
        "raw": "原文中的时间表达",
        "start": "2026-11-11T14:00:00+08:00",
        "end": "2026-11-11T15:00:00+08:00",
        "confidence": 0.92
      },
      "confidence": 0.9,
      "duplicateHint": "可能与已有记录重复时的说明，否则为 null"
    }
  ],
  "reply": "给用户的自然语言反馈"
}
```

约束：

- `entries` 为空时表示没有可记录内容；
- 时间无法解析时 `time` 为 `null`，类型不得为 `schedule`；
- `confidence < 0.6` 的条目在卡片上标注"需要核对"；
- 一条消息可拆多个条目，每条独立确认。

#### 4.3.3 时间解析规则

模型解析，代码校验。代码侧做三件事：校验 ISO 格式、校验是否在过去、校验起止是否颠倒。

| 表达               | 解析结果                                             | 说明                       |
| ------------------ | ---------------------------------------------------- | -------------------------- |
| 今天 / 明天 / 后天 | 当日 00:00 或原文时间点                              | 按本机时区                 |
| 下周三             | 下一个自然周的周三                                   | 若今天周三，"下周"指下一周 |
| 本周五             | 当前自然周的周五                                     | 已过则提示"本周已过"       |
| 下午两点           | 14:00                                                | 中文时间词映射             |
| 月底 / 月初        | 当月最后/第一天                                      | 置信度降低                 |
| 三天后             | 当前时间 +3 天                                       | 同时刻                     |
| 每周一             | `time.start` 为首个周一，附 `recurrence` 规则        | 检索时按窗口展开           |
| 每月 5 号          | `time.start` 为首个 5 号，附 `recurrence.byMonthDay` | 同上                       |
| 每个工作日         | 规则为 WEEKLY + 周一至周五                           | 同上                       |
| 每年生日           | 本期不展开为规则，只记为 `fact`                      | 见 4.3.7                   |
| 最近 / 有空 / 之后 | 无法解析，`time` 为 null                             | 降级为 plan 或 note        |

所有相对时间在确认卡片上**回显绝对时间**，用户核对后才入库。

#### 4.3.4 去重与冲突

抽取后、展示前，代码侧做两道检查：

1. **完全重复**：标题 + 类型相同，且内容相似度 > 0.9（用现有 cosine）→ 卡片提示"已存在相同记录"，只提供「忽略」与「仍然新建」。
2. **时间冲突**：新日程与已有 `active` 日程时间段重叠 → 卡片提示冲突，展示冲突条目摘要，由用户决定。

系统不自动合并、不自动覆盖。

#### 4.3.5 抽取 Prompt 骨架

```text
你是个人记忆助手。从用户的话里提取需要长期记住的信息。

当前时间：{now}，时区：{timezone}
已有相关记录（用于判重，仅供参考）：
{existingEntries}

规则：
1. 只提取与用户本人相关的事实、日程、规划。
2. 时间必须转换为带时区的 ISO 8601；无法确定就不填。
3. 一条话包含多个事件时拆成多条。
4. 不要编造用户没说的信息。
5. 只输出 JSON，不要附加解释。

输出结构：
{jsonSchema}
```

`existingEntries` 只注入最相似的 5 条，避免 prompt 过长。

#### 4.3.6 失败处理

| 失败              | 处理                                                           |
| ----------------- | -------------------------------------------------------------- |
| 返回非 JSON       | 重试一次；仍失败则提示"没能整理成记录"，保留原文，提供手动新建 |
| JSON 字段缺失     | 用默认值补齐，`confidence` 置 0.3 并标注需核对                 |
| 超时（> 15s）     | 同上                                                           |
| 一次抽取超过 5 条 | 只展示前 5 条，其余提示"还有 N 条未展示"                       |

#### 4.3.7 重复规则

支持 RRULE 的一个子集，够覆盖个人日程的常见表达：

| 频率      | 关键字段     | 覆盖表达                         |
| --------- | ------------ | -------------------------------- |
| `DAILY`   | `interval`   | 每天、每两天、每隔三天           |
| `WEEKLY`  | `byWeekday`  | 每周一、每周三和周五、每个工作日 |
| `MONTHLY` | `byMonthDay` | 每月 5 号、每月最后一天          |

不支持：每年重复、每月第 N 个周几、复杂例外（BYSETPOS）。遇到这些表达时降级为单次事件，并在卡片上提示"暂不支持该重复方式"。

**存储策略：不物化实例，只存规则。**

理由：一条"每个工作日"展开一年就是 260 条记录，既占空间又让修改变复杂。检索时按时间窗口现算实例，代价可控。

**展开规则（检索时执行）**

1. 输入时间窗口 `[windowStart, windowEnd]`；
2. 从 `recurrence` 规则推导窗口内所有实例；
3. 单条规则单次展开上限 60 个实例，超出截断并在结果里标记；
4. 重复必须有结束条件 `until`，抽取时缺省为录入时间 + 1 年；
5. 时区按本机，与单次事件一致。

**编辑语义（本期）**

- 修改或删除重复事件时，作用于整个系列；
- 不支持"只改这一次"，`exceptions` 字段预留但不启用（后续扩展）。

**抽取约束**

- 模型输出 `recurrence` 对象，字段见 5.1；
- 只说"每周一"没说具体时间 → 仍为 `schedule`，`start` 取该日 00:00，卡片标注"未指定具体时间"；
- 重复规则与具体时间必须同时回显在确认卡片上，例如"每周一 09:00，持续到 2027-11-06"。

#### 4.3.8 文档抽取为记录

用途：文档里已经有整理好的内容（简历、项目总结、年度计划），不必重新口述，直接从文档提取成条目。

**流程**

1. 用户在文档详情选择抽取范围：全文，或勾选指定块；
2. 按块批量送入抽取模型（每批 5 块），复用 4.3.2 的输出结构；
3. 候选条目进确认卡片，与对话录入使用同一组件；
4. 用户确认后入库，`source_type = 'document'`，`source_ref = docId`。

**参数与边界**

| 项           | 规则                                                    |
| ------------ | ------------------------------------------------------- |
| 单次候选上限 | 10 条，超出只展示前 10 条并提示剩余数量                 |
| 单次处理块数 | 100 块；超出提示分批                                    |
| 已抽取标记   | 块上记录 `extracted_at`，再次抽取时提示"该部分已抽取过" |
| 部分失败     | 单块失败跳过，其余继续，结束时汇总失败块数              |
| 去重         | 与已有条目走同一套去重与冲突提示（4.3.4）               |
| 文档删除     | 已抽取条目保留，引用处标注"来源文档已删除"              |

### 4.4 向量化

#### 4.4.1 模型与维度

沿用现有配置，不引入新依赖：

| 项   | 取值                           |
| ---- | ------------------------------ |
| 模型 | `embedding-3`（智谱）          |
| 维度 | 1536                           |
| 接口 | `POST {AI_API_URL}/embeddings` |
| 批量 | 10 条/批，批内并发             |

#### 4.4.2 什么进向量库

| 数据   | 是否向量化 | 向量文本                         |
| ------ | ---------- | -------------------------------- |
| 文档块 | 是         | 块内容（含标题路径前缀）         |
| 条目   | 是         | `标题 + 换行 + 内容`             |
| 消息   | 否         | 不向量化，避免记忆被对话噪音污染 |

#### 4.4.3 增量更新

- 条目修改标题或内容 → 重新生成该条向量，覆盖旧值；
- 条目状态变化 → 不重新向量化，检索时按状态过滤；
- 文档重新导入 → 删除旧块与旧向量，重建。

#### 4.4.4 降级

沿用现有机制：Embedding API 不可用时自动降级为 hash 向量（确定性伪随机）。

降级后的影响必须让用户知道：

- 语义检索退化为随机排序，仅 BM25 仍有意义；
- 界面在检索结果区显示提示"语义检索暂不可用，当前仅关键词匹配"；
- `isMockMode()` 为 true 时，cosine 阈值判断失效，直接返回 TopK 并标记低置信。

### 4.5 检索

#### 4.5.1 查询理解

一次轻量调用（可用小模型）解析问题，输出：

```json
{
  "needsPersonalContext": true,
  "timeRange": { "start": "2026-11-09", "end": "2026-11-15" },
  "keywords": ["Rust", "学习"],
  "entityTypes": ["schedule", "plan"]
}
```

规则：

- 通用知识问题（"什么是闭包"）→ `needsPersonalContext: false`，跳过个人检索；
- 含"我/我的/最近/这周"→ 强制为 true；
- 时间词按 4.3.3 同样规则解析；
- 解析失败时降级为：语义检索 + 最近 30 天的 active 条目。

#### 4.5.2 双通道检索

**通道 A：时间通道（确定性）**

分两步：单次事件走 SQL，重复事件在应用层展开。

```sql
-- 第一步：单次事件
SELECT id, type, title, content, start_at, end_at
FROM entries
WHERE status = 'active'
  AND type IN ('schedule', 'plan')
  AND recurrence IS NULL
  AND start_at IS NOT NULL
  AND start_at < :windowEnd
  AND COALESCE(end_at, start_at) >= :windowStart
ORDER BY start_at ASC
LIMIT 20;

-- 第二步：重复事件（取规则，应用层展开）
SELECT id, type, title, content, start_at, end_at, recurrence, recurrence_until
FROM entries
WHERE status = 'active'
  AND type = 'schedule'
  AND recurrence IS NOT NULL
  AND (recurrence_until IS NULL OR recurrence_until >= :windowStart)
LIMIT 200;
```

- 时间窗口由查询理解给出；
- 重复事件按 4.3.7 的规则展开后再过滤，展开结果参与同一套加权排序；
- 无时间语义的问题不启用此通道；
- 用户明确问"历史/上个月"时，状态过滤放宽到 `archived`。

**通道 B：语义通道（混合检索）**

沿用现有 `ragService.search`：

```
向量 TopK 15  ┐
              ├─ RRF 融合（k=60）→ 取 Top 20
BM25 TopK 15  ┘
```

- BM25 中文按 2-gram，英文按整词，适合精确术语；
- 向量捕捉同义表达；
- 两路都基于现有 `chunks` 表；条目向量需并入同一检索入口（见 5.1）。

#### 4.5.3 合并与排序

合并顺序按权重：

| 来源              | 权重 | 说明                           |
| ----------------- | ---- | ------------------------------ |
| 时间通道 · 日程   | 1.3  | 时间最确定，优先级最高         |
| 语义通道 · 条目   | 1.0  | 与问题语义相关                 |
| 语义通道 · 文档块 | 0.8  | 资料性内容，优先级低于个人记录 |

同一条目在两条通道都命中时只保留一次，取较高分。

最终排序：`score × 权重`，截断到 15 条；第 16 条起按类型汇总为一行。

#### 4.5.4 过滤规则

| 规则     | 说明                                                                    |
| -------- | ----------------------------------------------------------------------- |
| 状态过滤 | 默认只取 `active`；`draft` 永不参与                                     |
| 过期日程 | `archived` 且非历史查询 → 排除                                          |
| 阈值     | 真实 embedding 下 cosine < 0.35 丢弃；mock 模式关闭阈值                 |
| 数量上限 | 详细引用最多 15 条：条目最多 10 条，文档块最多 5 条；超出部分汇总为一条 |
| 去重     | 同一文档相邻块合并展示，只保留一次引用                                  |

#### 4.5.5 空结果

检索为空时：

- 不注入任何个人记录；
- 生成阶段强制走"未找到"话术；
- 界面提示"你的记录里没有相关内容"，并提供「记一条」快捷入口。

### 4.6 上下文组装

#### 4.6.1 Token 预算

| 部分           | 预算                         |
| -------------- | ---------------------------- |
| system prompt  | 约 300 token                 |
| 个人记录上下文 | 最多 3000 token              |
| 最近对话历史   | 最多 1500 token（最近 6 轮） |
| 用户当前问题   | 不限                         |

超预算时按优先级截断：时间通道日程 > 语义条目 > 文档块 > 历史对话。

单条记录超过 200 token 时截断，末尾加"……"。文档块单条上限 300 token，条目单条上限 120 token；15 条详细引用合计控制在 2400 token 以内，剩余 600 token 留给汇总行与格式开销。

#### 4.6.2 注入格式

带编号，便于模型引用：

```text
[个人记录]
1. [日程] 2026-11-11 14:00 提交 v5 方案（录入于 2026-11-06）
2. [规划] 前端工程化学习计划 · 进行中（录入于 2026-10-20，未设截止时间）
3. [事实] 偏好使用 TypeScript，不喜欢过度封装（录入于 2026-09-12）

[资料片段]
4. 《项目笔记 > 前端工程化 > 构建》构建流程使用 Vite，配置见 build.config.ts

[其他相关]
16. 另有 7 条与前端工程化相关的记录（3 条规划、4 条文档片段），已合并
```

超过 15 条时，多出的内容不逐条注入，而是按类型聚合为一行汇总，避免上下文被同类记录占满。汇总行也计入引用列表，用户可点击展开完整列表。

标签使用固定词表，模型据此区分来源类型。

#### 4.6.3 无记录时

不注入空标题，直接省略整段，并在 system prompt 中说明本条走"无依据"路径。

### 4.7 回答生成

#### 4.7.1 生成约束

写入 system prompt 的硬性规则：

```text
你是用户的个人助手，可以访问用户的个人记录。

规则：
1. 涉及用户个人信息时，只能依据下方 [个人记录] 和 [资料片段] 回答。
2. 每个来自个人记录的陈述后面必须标注编号，如 [1]。
3. 记录中没有的信息，明确说"你的记录里没有"，不要推测。
4. 通用知识可以正常回答，但必须与个人信息部分分开表述。
5. 多条记录冲突时，如实呈现，不擅自选择。
6. 不要暴露内部编号格式以外的系统细节。
```

#### 4.7.2 引用规则

| 情况       | 回答                         | 引用区                                  |
| ---------- | ---------------------------- | --------------------------------------- |
| 全部命中   | 直接回答                     | 展示全部来源                            |
| 部分命中   | 命中部分给结论，缺失部分明说 | 只展示命中来源，另标注"未命中：X"       |
| 全部未命中 | 明确说明没有记录             | 不展示引用区                            |
| 超过 15 条 | 前 15 条详细说明             | 第 16 条起汇总为一条"另有 N 条相关记录" |
| 通用问题   | 正常回答                     | 不展示引用区                            |

#### 4.7.3 输出结构

接口返回结构化字段，不依赖前端解析自然语言：

```json
{
  "reply": "这周你有 2 项待完成……",
  "citations": [
    { "type": "entry", "id": "e_123", "label": "提交 v5 方案", "snippet": "2026-11-11 14:00" },
    { "type": "chunk", "id": "c_88", "docName": "项目笔记", "headingPath": ["前端工程化", "构建"] }
  ],
  "missing": ["Rust 相关记录"],
  "degraded": false
}
```

### 4.8 引用溯源数据流

```
检索结果（带 id）
  → 与回答一起返回 citations
  → 前端点击引用
  → GET /api/entries/:id 或 GET /api/documents/:id/chunks/:chunkId
  → 展示完整条目字段 / 文档原文上下文（前后各 1 块）
```

引用必须保存快照：写入消息的 `metadata.citations`，避免条目后续被修改后，历史回答的引用对不上。

### 4.9 失败与降级矩阵

| 故障点               | 表现              | 降级行为                       | 用户可见提示                   |
| -------------------- | ----------------- | ------------------------------ | ------------------------------ |
| 意图判别失败         | 无法区分录入/问答 | 按包含问号判断，否则走录入     | 无                             |
| 抽取返回非法 JSON    | 无法生成条目      | 重试一次，仍失败转手动新建     | "没能整理成记录"               |
| Embedding API 不可用 | 语义检索失效      | hash 向量 + BM25               | "语义检索暂不可用"             |
| BM25 无结果          | 关键词不命中      | 只用向量结果                   | 无                             |
| 双通道均为空         | 无依据            | 走未找到话术                   | "记录中没有相关内容"           |
| 生成超时             | 无回答            | 返回检索结果列表，让用户自己看 | "回答生成超时，以下是相关记录" |
| 数据库不可用         | 全部失败          | 直接报错，不静默               | 明确错误码                     |

原则：**任何降级都不能让系统看起来正常但给出错误答案**。

### 4.10 成本与性能

> 模型选型、免费/付费路由、预算熔断与月度用量估算统一见第 10 节。本节只列单次操作的调用构成。

#### 4.10.1 调用次数

| 操作         | 模型调用                                              |
| ------------ | ----------------------------------------------------- |
| 录入一条消息 | 1 次抽取（+ 1 次 embedding）                          |
| 提一个问题   | 1 次查询理解（可用小模型）+ 1 次 embedding + 1 次生成 |
| 上传一份文档 | N 次 embedding（按批，10 条/批）                      |

#### 4.10.2 延迟目标

| 环节                                  | 目标                |
| ------------------------------------- | ------------------- |
| 文档分片                              | < 100ms / 万字      |
| 向量检索（1 万块内，SQLite 全表扫描） | < 300ms             |
| BM25（1 万块内）                      | < 150ms             |
| 抽取                                  | 依赖模型，目标 < 5s |
| 问答总耗时                            | 目标 < 8s           |

#### 4.10.3 优化手段

- 查询理解与生成可并行前置：先发起 embedding，同时做意图判断；
- 文档入库按批处理，批间不阻塞界面；
- 同一问题的检索结果做 5 分钟内存缓存（key = 问题 + 记录版本号）；
- 块数超过 2 万时切换 pgvector（现有双驱动已支持）。

### 4.11 评测

#### 4.11.1 用例集

建 20 条固定用例，覆盖：

| 类别     | 条数 | 例子                             |
| -------- | ---- | -------------------------------- |
| 时间查询 | 5    | "我这周有什么安排"、"下周三几点" |
| 规划状态 | 4    | "我那个学习计划进展如何"         |
| 事实偏好 | 4    | "我平时用什么技术栈"             |
| 无命中   | 3    | "我养过猫吗"（确实没有记录）     |
| 冲突     | 2    | 同一时段两条日程                 |
| 降级     | 2    | mock embedding 模式下的回答      |

#### 4.11.2 指标

- 命中率：应当被检索到的记录，实际被引用的比例；
- 引用准确率：引用内容与回答陈述一致的比例；
- 幻觉率：回答中出现记录里没有的个人事实的比例，**目标为 0**；
- 无命中识别率：应当说"没有"时确实说了的比例。

#### 4.11.3 回归方式

用例以 JSON 固化，跑批命令输出上述四项指标；每次修改 prompt 或检索参数后必须跑一遍。

## 5. 数据模型

### 5.1 新增表

```sql
CREATE TABLE IF NOT EXISTS entries (
  id            TEXT PRIMARY KEY,
  user_id       TEXT NOT NULL DEFAULT 'local',       -- 为登录预留
  library_id    TEXT NOT NULL DEFAULT 'default',     -- 为多库预留，本期只用 default
  type          TEXT NOT NULL CHECK(type IN ('schedule','plan','fact','note')),
  title         TEXT NOT NULL,
  content       TEXT NOT NULL DEFAULT '',
  status        TEXT NOT NULL DEFAULT 'draft'
                CHECK(status IN ('draft','active','done','archived')),
  start_at      INTEGER,          -- 毫秒时间戳，可空；重复事件为首个实例
  end_at        INTEGER,
  recurrence    TEXT,             -- JSON 规则，null 表示单次事件
  recurrence_until INTEGER,       -- 重复结束时间
  exceptions    TEXT,             -- 预留：例外实例，本期不使用
  source_type   TEXT NOT NULL DEFAULT 'conversation'
                CHECK(source_type IN ('conversation','document','manual')),
  source_ref    TEXT,             -- 会话 id 或文档 id
  confidence    REAL NOT NULL DEFAULT 1.0,
  created_at    INTEGER NOT NULL,
  updated_at    INTEGER NOT NULL,
  archived_at   INTEGER
);

CREATE INDEX IF NOT EXISTS idx_entries_status_type ON entries(status, type);
CREATE INDEX IF NOT EXISTS idx_entries_start ON entries(start_at) WHERE start_at IS NOT NULL;
CREATE INDEX IF NOT EXISTS idx_entries_library ON entries(library_id, status);
```

`recurrence` 的 JSON 结构：

```json
{
  "freq": "DAILY | WEEKLY | MONTHLY",
  "interval": 1,
  "byWeekday": ["MO", "WE", "FR"],
  "byMonthDay": 5,
  "until": 1798761600000
}
```

`freq` 为 `WEEKLY` 时用 `byWeekday`，为 `MONTHLY` 时用 `byMonthDay`，为 `DAILY` 时只用 `interval`。

```sql
CREATE TABLE IF NOT EXISTS entry_embeddings (
  entry_id   TEXT PRIMARY KEY,
  embedding  TEXT NOT NULL,      -- JSON 数组，1536 维
  model      TEXT NOT NULL,
  updated_at INTEGER NOT NULL,
  FOREIGN KEY (entry_id) REFERENCES entries(id) ON DELETE CASCADE
);
```

`documents`、`chunks`、`sessions`、`messages` 沿用现有表，补三个字段：

```sql
ALTER TABLE documents ADD COLUMN user_id TEXT NOT NULL DEFAULT 'local';
ALTER TABLE documents ADD COLUMN library_id TEXT NOT NULL DEFAULT 'default';
ALTER TABLE messages  ADD COLUMN citations TEXT;   -- JSON 快照
```

### 5.2 检索入口调整

现有 `ragService.search` 只查 `chunks`。v5 需要同时检索条目。

组件生成模块移除后，`search()` 不再需要保持旧签名兼容，直接重构为统一的检索入口 `searchAll()`：

- `vectorStore.similaritySearch()` → 文档块
- `entrySearch()` → 条目（读 `entry_embeddings` + BM25）
- `bm25Search()` → 文档块

三路结果统一走 RRF，再按 4.5.3 加权。`search()` 作为 `searchAll()` 的薄封装保留，供调试接口使用。

### 5.3 兼容

- 旧 `documents` / `chunks` 数据保留，补 `user_id = 'local'`；
- 组件生成相关表（`generator_states`、`agent_states`、`tool_calls`）随模块一起删除；
- 新增表通过 `CREATE TABLE IF NOT EXISTS` 幂等建表，本地无需迁移工具。

#### 用户消息

- 右对齐，主色背景，白字，最大宽度 72%；
- 支持多行，保留换行；
- 长文本超过 8 行折叠，点击展开。

#### 助手消息

- 左对齐，白底，细边框，最大宽度 78%；
- 正文支持 Markdown；
- 若为录入确认，消息体替换为抽取卡片，不显示自由文本。

#### 抽取卡片（核心交互）

结构自上而下：

1. 类型徽标（日程/规划/事实/笔记）+ 标题；
2. 字段行：时间（回显绝对值）、来源、置信度（低于 0.6 时显示"需要核对"）；
3. 冲突或重复提示条（可选，黄色）；
4. 操作行：确认入库（主按钮）、修改、忽略。

状态：

| 状态   | 表现                                          |
| ------ | --------------------------------------------- |
| 待确认 | 卡片正常，按钮可用                            |
| 已确认 | 卡片收起为一行"已记录：标题 · 时间"，绿点标记 |
| 已忽略 | 卡片收起为一行"已忽略"，灰点标记              |
| 修改中 | 卡片展开为表单，字段可编辑                    |
| 多条   | 卡片纵向排列，支持"全部确认"                  |

#### 引用区

- 位于助手消息底部，浅灰背景卡片；
- 每条引用一行：序号、名称、类型标签；
- 点击展开原文（抽屉 360px 右侧滑出），显示完整条目或文档前后文；
- 未命中时显示"未命中：Rust 相关记录"，灰字。

#### 输入区

- textarea 自适应高度，1 至 6 行；
- Enter 发送，Shift + Enter 换行；

## 10. 模型接入与成本策略

本节来自产品的定位转变：从练手项目转为个人真实使用。核心约束是用户定下的两条原则：

1. **能用免费的模型尽量用免费的；**
2. **需要付费的模型必须规划好使用量。**

由此推导三条工程原则：

3. 每次 AI 调用都记账（沿用现有 `costTracker`）；
4. 付费场景必须可降级，不允许"不付费就不能用"；
5. 预算超限自动切回免费档，不静默超支。

### 10.1 模型分层

| 层级          | 定位               | 候选                                              | 成本                 |
| ------------- | ------------------ | ------------------------------------------------- | -------------------- |
| T0 本地免费   | 离线兜底、隐私敏感 | Ollama 本地小模型（意图判别）、本地开源 embedding | 0                    |
| T1 云端免费   | 默认工作模型       | `glm-4-flash`（生成）、`embedding-3`（向量）      | 0，有限速            |
| T2 低价付费   | 质量升级档         | 各 provider 的轻量付费模型                        | 单价见配置文件 [TBD] |
| T3 高质量付费 | 手动切换的关键场景 | 各 provider 的旗舰模型                            | 单价见配置文件 [TBD] |

模型型号与价格由配置文件维护（`config/models.json`），不写死在代码和文档里——价格变化频繁，硬编码必然过期。

### 10.2 分场景路由

| 场景                | 默认                           | 可升级                        | 策略                   |
| ------------------- | ------------------------------ | ----------------------------- | ---------------------- |
| 意图判别 / 查询理解 | T0 本地小模型；未装则 T1 flash | 不升级                        | 永远免费               |
| 信息抽取            | T1 `glm-4-flash`               | T2（长文档批量抽取时手动选）  | 默认免费               |
| 问答生成            | T1 `glm-4-flash`               | T2 / T3（对话页切换）         | 默认免费               |
| 向量化              | T1 `embedding-3`               | T0 本地 embedding（离线场景） | 默认免费               |
| 时间解析 / 重复展开 | 纯代码计算                     | —                             | 不调模型               |
| 评测回归            | T1 flash                       | —                             | 月度固定消耗，计入预算 |

对话页提供三档模式切换：

| 模式         | 行为                                          |
| ------------ | --------------------------------------------- |
| 省钱         | 全部走 T0/T1，不触碰任何付费模型              |
| 均衡（默认） | 生成走 T1，单次回答可手动点"用更好的模型重答" |
| 质量         | 生成走 T3，仍受预算熔断约束                   |

### 10.3 使用量估算

按三档个人使用强度估算（30 天）：

| 项目        | 轻度             | 中度 | 重度 |
| ----------- | ---------------- | ---- | ---- |
| 对话轮次/天 | 10               | 20   | 40   |
| 录入条数/天 | 3                | 5    | 10   |
| 文档导入/周 | 1 篇（约 50 块） | 2 篇 | 5 篇 |

推算月度调用量：

| 调用类型            | 轻度       | 中度         | 重度         |
| ------------------- | ---------- | ------------ | ------------ |
| 查询理解            | 300        | 600          | 1,200        |
| 生成回答            | 300        | 600          | 1,200        |
| 信息抽取            | 90         | 150          | 300          |
| embedding（查询）   | 300        | 600          | 1,200        |
| embedding（文档块） | 150        | 300          | 750          |
| embedding（条目）   | 90         | 150          | 300          |
| **生成模型合计**    | **690 次** | **1,350 次** | **2,700 次** |
| **embedding 合计**  | **540 次** | **1,050 次** | **2,250 次** |

生成 token 估算（中度档）：每次生成平均输入约 2,500 token（上下文预算 3,000，通常不会打满）、输出约 400 token，月度约 **600 × 2,900 ≈ 174 万 token**。

**结论**

- 默认全走 T1 免费档：**月成本 0**。代价是免费档的限速，高峰期排队，体验可接受；
- `embedding-3` 免费额度是否覆盖中度档月约 1,050 次调用，需要查账号实际额度 [TBD]；不覆盖时降级顺序为本地 embedding → hash 向量，功能不中断；
- 付费只发生在主动切质量模式。假设质量模式占生成调用的 20%（中度档约 120 次/月），月成本 = `120 × 2,900 token × T3 单价`，单价填入配置文件后可自动算出；
- 建议设置月度付费预算红线（默认 10 元，可配置）。

### 10.4 预算控制机制

在现有 `costTracker`（`ai_usage_logs` 表 + 每日 token 预算）上扩展：

| 机制         | 现状                                         | 新增                                                                           |
| ------------ | -------------------------------------------- | ------------------------------------------------------------------------------ |
| 用量记录     | 每次调用异步入库（feature / model / tokens） | 补 `provider` 与按单价表算出的 `cost` 字段                                     |
| 每日预算     | `DAILY_TOKEN_BUDGET` 告警                    | 保留                                                                           |
| 月度金额预算 | 无                                           | `MONTHLY_COST_BUDGET`（默认 10 元），累计含付费模型估算成本                    |
| 熔断         | 无                                           | 调用前检查本月累计：达 80% 界面警告，达 100% 强制路由到 T1 免费模型            |
| 单价表       | 无                                           | `config/models.json` 维护 provider + model + 输入/输出单价，支持按生效日期分段 |
| 用量页       | 现有 cost breakdown                          | 加"本月预计花费"与预算进度条                                                   |

### 10.5 本地模型（T0，P1）

- 启动时检测本地 Ollama（默认端口），可用则启用本地小模型承担意图判别与查询理解；
- 可选开启本地开源 embedding，开启后向量化完全离线；
- 不是默认路径：机器不够时不装，全部走 T1，产品照常可用。

### 10.6 降级链

任何付费调用失败或触发预算熔断时：

```
T3 → T2 → T1（glm-4-flash）→ T0（本地，若可用）
```

embedding 额外保留现有的 hash 向量降级作为最后兜底（检索质量下降但功能不断）。

底线重申：**录入、检索、问答三个核心功能在 T1 免费档必须完整可用。付费只提升回答质量，不解锁功能。**
